# PS26145 — Model Selection per Detector
**Scope:** Choose and compare candidate model families for each detection problem, within the already-recommended Rules + Classifiers hybrid architecture. No training is performed here — this is model selection only, ending in an MVP / Alternative / Optional-Advanced recommendation per detector.

**Architecture reminder carried forward:** rules remain the primary detector for DDoS and reconnaissance (per the rule-baseline evidence); a classifier is the primary need for C2 beaconing, encrypted-session malware, and the evasive cases of DGA/DNS tunnelling/exfiltration. For DDoS/recon, ML is evaluated below as an **optional corroborating layer**, not a replacement for the rule.

---

## 0. Cross-Cutting Notes (apply to every candidate below unless stated otherwise)

- **Balancing methods considered generically:** class weighting (penalize misclassifying the minority attack class more heavily in the loss), random/synthetic oversampling of the minority class (e.g., SMOTE-family techniques) or undersampling of the (much larger) benign class, and threshold adjustment post-training rather than resampling at all. Which specific combination suits each detector is called out per-candidate, since the *degree* of imbalance genuinely differs (e.g., DDoS attack windows are dense once active, whereas C2 beacon events are sparse relative to a long observation horizon).
- **Thresholding, in general:** every classifier here outputs a continuous score; a decision threshold converts that into an alert. Thresholds are tuned on a held-out validation split to hit a target precision/recall trade-off (e.g., prioritizing low false-positive rate for high-volume classes like DDoS, per the PS's own FPR framing from the requirements task) — this document specifies *that* thresholding is needed and on what basis, not the specific tuned values, since no training has occurred.
- **Computational requirements / inference latency** are described relatively (lightweight vs. heavier), since actual numbers depend on hardware and implementation not yet chosen.
- Temporal models (LSTM/GRU/Temporal CNN/Transformer) are only proposed **where a detector's raw sequence data plausibly carries information a hand-engineered summary statistic loses** — consistent with the task's "temporal only where justified" instruction. Where the engineered features (from the feature-engineering task) already capture the relevant signal well, a temporal model is listed only as an optional-advanced upgrade, not the MVP.

## 1. DDoS (rule-primary; ML as optional corroboration)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Logistic Regression** | `dst_packet_rate`, `dst_byte_rate`, `syn_no_completion_ratio`, `src_ip_entropy_toward_dst`, `unique_src_count_toward_dst` | Binary probability (DDoS vs. benign) per destination-window | Binary cross-entropy | Class weighting (benign heavily outnumbers active-attack windows) | Standard probability cutoff, tuned on validation precision/recall | Very low | Very low (a handful of multiplications) | **Excellent** — coefficients map directly to feature contributions, easy to justify in a report | Strength: trivial to explain and deploy; Weakness: assumes roughly linear separability, may miss non-linear interactions between rate and entropy that a genuine flood produces |
| **Random Forest** | Same features | Binary probability | Gini/entropy impurity | Class weighting or balanced bootstrap sampling per tree | Same validation-based cutoff | Low-moderate | Low | Good — feature importances and per-tree paths are interpretable, though less directly than logistic regression's coefficients | Strength: captures non-linear threshold interactions rules alone can't express (e.g., "rate is only suspicious *combined with* low entropy diversity"); Weakness: larger model, marginal latency cost over logistic regression for a threat rules already handle well |
| **XGBoost/LightGBM** | Same features | Binary probability | Log loss with optional focal-loss-style reweighting | Built-in `scale_pos_weight`/class-weight support | Same | Low-moderate | Low | Good, via feature-importance/SHAP, though gradient-boosted trees are slightly less directly interpretable than a single random forest path | Strength: typically the strongest tabular performance of the classical options for a given amount of tuning; Weakness: more hyperparameters to tune under hackathon time pressure than Random Forest |

**MVP MODEL:** Rule baseline remains primary (per architecture decision); **Random Forest** as the corroborating classifier — a good balance of handling non-linear feature interaction over Logistic Regression, without the extra tuning burden of gradient boosting, for a threat where rules already do most of the work.
**ALTERNATIVE:** XGBoost/LightGBM — marginally stronger ceiling if time allows tuning, otherwise not clearly worth the extra effort here.
**OPTIONAL ADVANCED MODEL:** A lightweight **Temporal CNN** over the short-window rate/entropy time series (rather than a single-snapshot feature vector), to capture the *shape* of a rate ramp-up (sudden vs. gradual onset) — justified only as a refinement, since the rule and classical-feature classifier already cover the primary signal well.

## 2. C2 Beaconing (classifier-primary)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Random Forest / XGBoost** on engineered features | `periodicity_score_pair`, `interarrival_mean/variance_pair`, `destination_repeat_count_pair`, `flow_size_consistency_pair`, `unique_destination_count_src` | Binary probability (beaconing vs. benign) per (src,dst) pair | Log loss, class-weighted | Class weighting — beacon pairs are rare relative to all observed pairs over a long horizon | Validation-tuned cutoff, likely favoring recall given beaconing's stealthy nature | Low | Low (feature vector already summarized) | Good — feature importance directly names "periodicity" or "repeat count" as the driver, matching the alert's required evidence | Strength: builds directly on already-engineered features that hand-encode the domain knowledge (regularity, repetition); Weakness: relies entirely on the engineered periodicity score being a good enough summary — deliberately jittered/evasive beaconing may need richer sequence information than a single coefficient-of-variation-style feature captures |
| **LSTM / GRU** over raw inter-arrival-time sequence | Raw ordered `packet_timestamps`-derived inter-arrival sequence per (src,dst) pair (not the pre-summarized periodicity score) | Binary probability | Binary cross-entropy | Class weighting, or oversampling of confirmed beacon sequences from the sandboxed-emulator lab data | Same validation-based approach | **Higher** — recurrent processing over a sequence, more parameters | **Higher** — sequential computation adds latency versus a single feature-vector lookup, a real tension against the PS's bounded-latency requirement | Weaker directly, though attention/gate-activation visualization can partially recover some interpretability | Strength: can learn subtler timing patterns than a single hand-engineered CV statistic, particularly useful against jittered/evasive beaconing that a fixed periodicity formula underrates; Weakness: needs more data to train well, adds latency and complexity that must be justified by a measurable accuracy gain over the classical option |

**Justification for including a temporal model here:** this is one of the two threats flagged in the architecture task as *fundamentally* a sequence/shape problem — the periodicity feature is a reasonable engineered summary, but it is still a single hand-chosen statistic, and adversarial jitter is specifically designed to defeat exactly that kind of fixed-formula summary. A model that sees the raw sequence has a structural chance of doing better here that a purely tabular model does not.

**MVP MODEL:** **Random Forest (or XGBoost) on the engineered periodicity/repeat/consistency features** — directly buildable from data already produced by the feature-engineering task, fast, and explainable, giving a credible working detector without the added latency/complexity of a recurrent model.
**ALTERNATIVE:** XGBoost in place of Random Forest if the classical-feature signal proves non-linear enough to benefit from boosting.
**OPTIONAL ADVANCED MODEL:** **GRU** (lighter-weight than LSTM, generally comparable accuracy on shorter sequences, a reasonable compute/quality trade-off) over the raw inter-arrival sequence, positioned explicitly as a stretch goal to demonstrate improved robustness against jittered beaconing that the classical feature-based model may miss — a natural "does ML add value beyond the simple ML" comparison, one level up from the rule-vs-ML comparison already established.

## 3. DGA Domains (classifier-primary)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Logistic Regression** on `domain_char_entropy`, `domain_ngram_score`, `domain_length` | Per-query engineered features | Binary probability (DGA vs. benign) per query | Binary cross-entropy | Class weighting (DGA queries rare among all DNS traffic) | Validation-tuned cutoff | Very low | Very low | Excellent | Strength: fast, simple, matches the rule baseline's own logic closely enough to be a natural first upgrade; Weakness: same blind spot as the rule — wordlist-style/dictionary DGA families that don't produce high entropy or unusual n-gram scores will likely also evade this model, since it uses the same two features the rule does |
| **Random Forest / XGBoost** on the same features plus `nxdomain_ratio_host`, `query_rate_host`, `unique_domain_count_host` | Combines per-query lexical features with per-host behavioral features | Binary probability | Log loss, class-weighted | Same | Same | Low | Low | Good, via feature importance | Strength: combining lexical *and* behavioral host-level signals gives more separation than lexical features alone — a host querying several borderline-entropy domains in a burst is more suspicious than one such query in isolation, which this model can capture and the pure-lexical model cannot; Weakness: still bounded by the quality of the underlying entropy/n-gram/behavioral features |
| **Character-level CNN or LSTM** directly on the raw `query_name` string | Raw domain-name character sequence (not pre-summarized entropy/n-gram score) | Binary probability | Binary cross-entropy | Class weighting or oversampling of DGArchive-sourced positive examples | Same | Moderate | Low-moderate (short strings, fast per-query inference) | Weaker — character-level model internals are harder to translate into the alert's evidence field than "entropy exceeded X" | Strength: this is a well-established, genuinely justified use of a sequence model — character-level patterns (e.g., specific consonant clusters, positional character statistics) that a single entropy/n-gram scalar cannot fully capture are exactly what a char-CNN/LSTM is good at, and is precisely the family of DGA (dictionary/wordlist-based) that evades entropy-based methods; Weakness: needs enough labeled examples per DGA family to learn generalizable character patterns, and is the least explainable of the three options |

**MVP MODEL:** **Random Forest (or XGBoost) combining lexical + host-behavioral engineered features** — the best balance of catching more than the rule/logistic-regression combination alone, while remaining fast and explainable via feature importance.
**ALTERNATIVE:** Logistic Regression alone, if time is extremely constrained — a legitimate, defensible fallback given how close it already is to the rule baseline's own logic.
**OPTIONAL ADVANCED MODEL:** **Character-level CNN** over the raw domain string — the clearest sequence-model justification of the three "classifier-primary" threats besides C2, specifically to catch dictionary/wordlist-style DGA families that entropy/n-gram scoring is known to under-detect.

## 4. DNS Tunnelling (classifier-primary, though rule performs reasonably on obvious cases)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Random Forest / XGBoost** | `query_length_avg/max_host`, `record_type_distribution_host`, `response_size_avg_domain`, `query_concentration_host_domain` | Binary probability (tunnelling vs. benign) per (host, domain) pair | Log loss, class-weighted | Class weighting | Validation-tuned cutoff | Low | Low | Good, via feature importance directly naming the evidence (e.g., "elevated TXT-record fraction") | Strength: this threat's engineered features already capture the relevant statistical shape well (length, record-type mix, concentration); a tree ensemble over them should comfortably beat the rule's fixed thresholds by learning combined/non-linear thresholds; Weakness: still limited by the same feature set the rule uses — a tunnel deliberately engineered to keep every individual feature just under a "normal-looking" value on all axes simultaneously could still evade both |
| **Extra Trees** | Same features | Binary probability | Same | Same | Same | Low | Low | Similar to Random Forest | Strength: often trains faster than Random Forest with comparable accuracy due to more randomized splits, a minor hackathon-time advantage; Weakness: no clear accuracy edge over Random Forest for this feature set, mainly a training-speed trade-off |

**Note on temporal models here:** unlike C2/encrypted-malware, DNS tunnelling's core signal (query length, record-type mix, concentration) is already well captured by aggregate statistics over a window — there isn't a strong justification for a sequence model unless a future iteration wants to model the *order* of record types or query timing within a session, which isn't established as necessary by anything in the threat-decomposition or feature-engineering tasks. No temporal model is proposed as even an optional-advanced choice here.

**MVP MODEL:** **Random Forest** on the engineered features — directly improves on the rule baseline's fixed thresholds by learning combined feature interactions, with strong explainability via feature importance.
**ALTERNATIVE:** **Extra Trees** — comparable accuracy, faster to train, a reasonable swap if hackathon time is tight.
**OPTIONAL ADVANCED MODEL:** **XGBoost/LightGBM** tuned more carefully than the MVP's default settings — a incremental-quality upgrade path rather than a structurally different approach, appropriate as a stretch goal rather than a necessity.

## 5. Encrypted-Session Malware (classifier-primary, clearest ML necessity alongside C2)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Random Forest / XGBoost** on engineered summary features | `ja3_rarity_score`, `packet_size_prefix_mean/variance`, `interpacket_timing_prefix_mean/variance`, `sni_present_flag`, `session_duration_so_far` | Binary probability (malicious vs. benign session) | Log loss, class-weighted | Class weighting; malicious-emulated sessions likely far rarer than benign TLS traffic in the lab dataset | Validation-tuned cutoff | Low | Low | Good via feature importance | Strength: fast, deployable, clearly beats the rule baseline's two-variance heuristic by learning non-linear combinations of the same summary statistics; Weakness: still working from *summarized* prefix statistics (mean/variance of the first N packets) rather than the full ordered sequence, so it may miss patterns that live specifically in the *order* of packet sizes/timings rather than their aggregate distribution |
| **Temporal CNN** over the raw packet-size + inter-arrival-time prefix sequence | Raw ordered `packet_sizes`/`packet_timestamps` prefix (bounded length, per the feature-engineering task's design) | Binary probability | Binary cross-entropy | Class weighting or oversampling | Same | Moderate | Low-moderate (a 1D convolution over a short, bounded-length sequence is cheap relative to a recurrent model) | Weaker than trees, though saliency/activation-based inspection can partially recover interpretability | Strength: **this is the single most directly justified sequence-model use case of all seven detectors** — the threat-decomposition task explicitly identified "does this encrypted session's shape resemble malware C2" as fundamentally a pattern-recognition problem over the packet-size/timing sequence, which is exactly the input a temporal CNN operates on directly, without the lossy summarization step the classical option requires; Weakness: needs enough labeled malicious-emulated sessions across varied traffic-shaping patterns to generalize, and a bounded-length 1D CNN is a reasonable middle ground between full sequence models and none at all |
| **LSTM/GRU** over the same raw sequence | Same input | Same output | Same | Same | Same | **Highest of the credible options** for this threat | **Highest** — recurrent processing is slower than a 1D convolution over the same bounded sequence | Similar to Temporal CNN, slightly weaker | Strength: can in principle capture longer-range dependencies in the sequence than a CNN's fixed receptive field; Weakness: for the *short, bounded-length* prefixes this design already uses, a Temporal CNN captures most of the same information at lower latency cost, making the extra recurrent complexity hard to justify for a first prototype |

**MVP MODEL:** **Random Forest (or XGBoost)** on the engineered summary-statistic features — fast, explainable, and a genuine improvement over the rule's blocklist-plus-two-variance heuristic, usable as a credible working detector without committing to sequence-model complexity up front.
**ALTERNATIVE:** XGBoost/LightGBM if the summary-statistic feature set shows non-linear structure worth the extra tuning.
**OPTIONAL ADVANCED MODEL:** **Temporal CNN** over the raw bounded packet-size/timing prefix sequence — the strongest-justified temporal model in the entire system, specifically because this threat's detection basis was identified from the very first threat-decomposition task as inherently sequence-shaped, not just summary-statistic-shaped; recommended over LSTM/GRU for this bounded-length input given the better latency/complexity trade-off.

## 6. Reconnaissance / Port Scanning (rule-primary; ML as optional corroboration)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Logistic Regression / Random Forest** | `unique_dst_port_count_src`, `unique_dst_host_count_src`, `scan_attempt_rate_src`, `flow_completion_ratio_src` | Binary probability (scanning vs. benign) per source | Log loss, class-weighted | Class weighting | Validation-tuned cutoff | Very low | Very low | Excellent (Logistic Regression) to Good (Random Forest) | Strength: fan-out features are already strongly separating on their own (per the rule-baseline task's own assessment), so either simple model comfortably improves on a fixed threshold by learning the right combined cutoff; Weakness: neither addresses the rule's core blind spot — slow/low-rate scanning paced below detection thresholds over a longer horizon than this detector's short window covers |

**Note:** no gradient-boosted or temporal option is separately justified here beyond Random Forest — this threat's signal (fan-out counts, rate, completion ratio) is simple and already well-separated, so the marginal value of a heavier model is low, consistent with this being (alongside DDoS) one of the two threats where rules already go furthest.

**MVP MODEL:** Rule baseline remains primary; **Logistic Regression** as a lightweight corroborating classifier, chosen over Random Forest here specifically because the signal is simple enough that the added interpretability and near-zero compute cost outweighs Random Forest's marginal non-linearity benefit for this particular threat.
**ALTERNATIVE:** Random Forest, if validation shows a meaningful non-linear interaction between fan-out and rate features worth capturing.
**OPTIONAL ADVANCED MODEL:** None proposed — this threat does not present a strong case for anything beyond the classical options above; effort is better spent elsewhere (per the architecture recommendation's core rationale of concentrating ML effort where it's needed).

## 7. Data Exfiltration (classifier-primary for the evasive case; anomaly detection justified as a complement)

| Candidate | Input | Output | Objective/Loss | Balancing | Thresholding | Compute | Latency | Explainability | Strengths/Weaknesses |
|---|---|---|---|---|---|---|---|---|---|
| **Random Forest / XGBoost** (supervised) | `outbound_inbound_byte_ratio_flow`, `cumulative_outbound_volume_host`, `destination_novelty_flag`, `outbound_baseline_deviation_host` | Binary probability (exfiltration vs. benign) per flow/host | Log loss, class-weighted | Class weighting | Validation-tuned cutoff | Low | Low | Good via feature importance | Strength: learns combined, non-linear thresholds across ratio/volume/novelty/deviation better than the rule's separate branch logic; Weakness: still a supervised model bounded by what the lab's simulated exfiltration scenarios actually cover — a genuinely novel exfiltration pattern outside the training distribution (e.g., a slow-drip technique the lab never generated) is a real blind spot |
| **Isolation Forest** (unsupervised anomaly detection) | Same feature set, or a broader per-host behavioral feature set, without requiring labeled attack examples | Anomaly score (higher = more anomalous), not a class probability | Isolation-based partitioning objective (no explicit loss function in the classification sense) | Not applicable in the same sense — trained only (or mostly) on benign/normal data by design, which sidesteps the imbalance problem entirely rather than solving it | Threshold on anomaly score, tuned on validation to control false-positive rate | Low | Low | Weaker — an anomaly score alone doesn't say *why* a flow is anomalous as directly as a supervised feature-importance explanation does, though the specific feature(s) driving isolation depth can be partially recovered | Strength: **genuinely justified here** — exfiltration is the one threat among the seven where the space of possible evasive behaviors (novel low-and-slow patterns, unusual destinations, atypical timing) is large enough that relying solely on labeled lab-generated examples risks missing real-world variants; an anomaly layer catches "this host's behavior is unlike anything normal," complementing rather than replacing the supervised model; Weakness: needs a well-defined "normal" baseline (per-host or global) to train against, and doesn't map as cleanly onto the alert schema's expected evidence, needing a translation step |
| **Autoencoder** (unsupervised anomaly detection, lightweight alternative to Isolation Forest) | Same feature set, reconstructed through a compressed representation; anomaly = high reconstruction error | Continuous anomaly score (reconstruction error) | Mean-squared reconstruction error | Same as Isolation Forest — trained on normal/benign data | Threshold on reconstruction error, validation-tuned | Moderate (more compute than Isolation Forest to train, though inference is a single forward pass and still fast) | Low at inference | Similar weakness to Isolation Forest — reconstruction error doesn't directly name a cause | Strength: can capture more complex, non-linear "normal" manifolds than Isolation Forest's axis-aligned partitioning, if the feature set has meaningful non-linear structure; Weakness: more to tune (architecture, training) for a benefit that, given this feature set is already fairly low-dimensional and engineered, may not clearly exceed Isolation Forest's simpler approach |

**MVP MODEL:** **Random Forest (or XGBoost), supervised**, on the engineered ratio/volume/novelty/deviation features — directly builds on and improves the rule baseline's branch logic, remains explainable, and covers the exfiltration patterns the lab can actually generate and label.
**ALTERNATIVE:** XGBoost/LightGBM in place of Random Forest for a marginal accuracy ceiling if tuning time allows.
**OPTIONAL ADVANCED MODEL:** **Isolation Forest** run in parallel as an unsupervised complement — the clearest justified use of anomaly detection among all seven threats, specifically to catch exfiltration patterns the lab's labeled scenarios don't anticipate, chosen over an Autoencoder for this feature set given the lower tuning burden and comparable expected benefit on a modestly-dimensional, already-engineered feature space.
