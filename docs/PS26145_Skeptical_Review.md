# PS26145 — Skeptical Technical Review (Adversarial Judge Pass)
**Role:** SIH technical evaluator, not a design contributor. This document identifies weaknesses only. No new modules are proposed; fixes are the minimum practical action, and "None for MVP" is used where a full fix is genuinely out of scope for a prototype.

---

### Issue 1 — Encrypted-malware demo is a rigged known-answer test
**Category:** Real Technical Problem
**Severity:** High
**Why it matters:** Demonstrating detection via a fingerprint pre-added to a blocklist proves nothing about the system's ability to catch *unknown* encrypted malware — the actual, harder problem the PS asks for. A technically literate judge will recognize this as "you showed me the one case you already knew the answer to," not evidence of a working detection capability.
**Evidence/reasoning:** The demo script itself states the ML classifier for this threat was descoped due to a training-data gap, leaving only a static blocklist match as the live-demonstrable path.
**Required fix:** None for MVP beyond what's already planned — state this limitation explicitly and proactively in the demo narration (already scripted), rather than let a judge discover it by questioning.

---

### Issue 2 — DoH/DoT is a real blind spot, not an edge case
**Category:** Real Technical Problem
**Severity:** High
**Why it matters:** DGA and DNS-tunnelling detection depend entirely on visible plaintext DNS query names. Encrypted DNS (DoH/DoT) is now a default or common option in major browsers and operating systems, not a rare configuration — meaning a purely passive detector built on this assumption could be blind on a meaningful fraction of real-world modern traffic, not just a theoretical corner case.
**Evidence/reasoning:** The data-model and data-requirements work explicitly flags DoH/DoT as removing query-name visibility, but every subsequent task treats this as a documented caveat rather than a capability limitation with real, current-day prevalence.
**Required fix:** None for MVP (lab traffic is plaintext DNS by design); the submission should state this limitation as a known constraint of passive metadata-only detection, not bury it in a data-model footnote.

---

### Issue 3 — All ML validation is against synthetic, tool-generated attacks
**Category:** Real Technical Problem
**Severity:** Critical
**Why it matters:** Every reported metric (Macro F1, PR-AUC, FPR) is measured against traffic generated by a small, fixed set of open-source tools (hping3, a sandboxed C2 emulator, dnscat2/iodine, DGArchive). Real attackers deliberately evade known tool signatures. Configuration-holdout testing varies *parameters* of the same tools, not fundamentally different attacker behavior — it does not demonstrate generalization to real adversarial traffic.
**Evidence/reasoning:** The dataset-evaluation task itself acknowledges domain-shift risk for nearly every source, but no task ever quantifies how severe this risk is or tests against genuinely out-of-distribution attack behavior.
**Required fix:** None for MVP (out of scope for a hackathon timeline); the submission must state performance numbers as "measured on lab-synthetic traffic" explicitly, never imply they represent real-world accuracy.

---

### Issue 4 — False-positive rate targets ignore the base-rate problem
**Category:** Real Technical Problem
**Severity:** High
**Why it matters:** A committed FPR of 10-15% sounds acceptable as a rate, but with benign traffic vastly outnumbering attack traffic (an explicitly stated project assumption), even a "low" FPR produces an overwhelming absolute number of false alerts per day at realistic traffic volumes — the classic base-rate fallacy. Nowhere in the project is this translated into an expected alert-volume-per-day figure a SOC could actually operate with.
**Evidence/reasoning:** Every FPR target across the model-development methodology and verification strategy is stated as a percentage, never converted to an absolute expected false-alert count against a realistic traffic baseline.
**Required fix:** None for MVP; state FPR as a rate only, and explicitly caveat in the submission that absolute alert volume at production scale has not been estimated.

---

### Issue 5 — "Real-time" C2 detection cannot be shown live in real time
**Category:** Acceptable Prototype Limitation
**Severity:** Medium
**Why it matters:** C2 beaconing detection genuinely requires an hours-long observation horizon. The demo's own design admits this by using accelerated replay rather than a live trigger — which is honest, but it also means the "near-real-time" claim has never actually been demonstrated live for this threat, only simulated at compressed speed.
**Evidence/reasoning:** The demo-strategy document explicitly states this design choice and its reasoning.
**Required fix:** None for MVP — the underlying pipeline logic is genuinely incremental/causal; only the demo's ability to show a multi-hour process in a short slot is limited, which is an inherent property of the threat, not a flaw in the architecture.

---

### Issue 6 — Throughput/latency targets are asserted, not yet measured
**Category:** Real Technical Problem
**Severity:** High
**Why it matters:** The committed figure of at least 2,000 flows/sec with p95 latency under 2 seconds is stated as a "team target," but no documented engineering estimate ties this number to the actual chosen stack (Python `asyncio` plus Redis Streams), and the benchmark itself had not been executed as of the most recent project review. Presenting an unmeasured target as if it were a demonstrated capability would be an unsupported claim.
**Evidence/reasoning:** The final audit explicitly flags that no capacity estimate exists for this figure, and the verification strategy's benchmark execution was still outstanding at last review.
**Required fix:** Run the throughput/latency benchmark before the demo and report the actual measured number — if it differs from the target, the demo and submission materials must use the real number, not the original target.

---

### Issue 7 — Single-host resource contention threatens live timing claims
**Category:** Acceptable Prototype Limitation
**Severity:** Medium
**Why it matters:** Every component — traffic generators, capture, the full pipeline, the backend, and the dashboard — runs on one host during the demo. Under simultaneous live load (several attack scenarios plus continuous benign traffic plus dashboard rendering), CPU contention could delay feature computation past a detection window, causing a visibly slow or missing alert in front of judges — directly undercutting the near-real-time claim at the worst possible moment.
**Evidence/reasoning:** The single-host Docker Compose design was explicitly chosen for simplicity over the original multi-VM lab; this trade-off was correctly identified for feasibility but its live-demo timing risk was not separately addressed.
**Required fix:** Rehearse the exact demo sequence on the actual demo hardware at least once with all components running simultaneously (already partially covered by the demo checklist's rehearsal requirement) to surface resource contention before judging, not during it.

---

### Issue 8 — The sandboxed C2 emulator tool has never actually been chosen
**Category:** Real Technical Problem
**Severity:** Medium-High
**Why it matters:** C2 beaconing detection — one of the harder, more scientifically interesting detectors — depends on a "sandboxed C2 emulator" that was flagged as an open team decision in the earliest lab-architecture task and remains undecided as of the most recent audit. A load-bearing capability's data source is still not concretely specified this late in the design process.
**Evidence/reasoning:** Every subsequent task (lab architecture, dataset evaluation, rule baseline, model selection, capability classification) refers to this tool only generically, never naming a specific implementation.
**Required fix:** Select a specific, concrete emulator tool before beginning C2 data generation — this is a decision, not new engineering scope.

---

### Issue 9 — DGArchive access/licensing terms were never actually confirmed
**Category:** Real Technical Problem
**Severity:** Medium
**Why it matters:** If DGArchive access requires an application process, institutional agreement, or has usage restrictions incompatible with a hackathon submission, the DGA detector's primary data source could be unavailable entirely — a hard blocker discovered too late to fix.
**Evidence/reasoning:** The dataset-evaluation task explicitly notes "licensing terms should be checked before use" but no subsequent task confirms this was actually done.
**Required fix:** Confirm access terms immediately; if restricted, substitute a different published, openly-licensed DGA algorithm list (several exist) rather than depending on an unconfirmed source.

---

### Issue 10 — Severity weights are arbitrary constants dressed as a formula
**Category:** Acceptable Prototype Limitation
**Severity:** Low-Medium
**Why it matters:** The severity calculation multiplies a "team-authored, not derived from any dataset" base weight per threat class by a confidence tier and a magnitude factor. This looks rigorous but is not empirically calibrated — a judge probing "how did you decide DDoS is weighted higher than reconnaissance" will get "we decided so," not a data-backed answer.
**Evidence/reasoning:** The alert-architecture task states this plainly itself.
**Required fix:** None for MVP; state the weights are a documented, reasoned starting point, not empirically derived, if asked — do not imply otherwise.

---

### Issue 11 — Audit-readiness is currently aspirational, not implemented
**Category:** Real Technical Problem
**Severity:** Medium
**Why it matters:** Model-integrity and dataset-integrity hash fields, along with specific audit-event types, were classified MVP-required in the security review but, as of the most recent audit, had not yet been added to the actual persistence-layer schema. Claiming "audit-ready" logging in a submission before this is implemented would overstate current system state.
**Evidence/reasoning:** The second final audit explicitly lists this as an open, unresolved item (B1).
**Required fix:** Add the hash columns and audit-event types to the persistence layer before claiming this capability in the submission or demo.

---

### Issue 12 — Explanation-text correctness is validated only by static example, not systematically
**Category:** Acceptable Prototype Limitation
**Severity:** Low
**Why it matters:** The per-threat explanation templates were checked against one hand-picked example each. No test verifies the template renders sensibly across the full range of real evidence-value combinations (e.g., a zero, a negative, or an extreme outlier value in a slot). A malformed sentence in a live demo (even if not "fabricated," just nonsensical) undercuts the credibility of the explanation feature.
**Evidence/reasoning:** The verification strategy's test suite does not include a property-based or boundary test for template rendering across the evidence-value range.
**Required fix:** Add a small boundary-value test (zero, extreme, and negative-where-applicable values) for each template before the demo — low effort, meaningfully reduces demo risk.

---

### Issue 13 — Reconnaissance/DDoS features assume response-side visibility that isn't guaranteed
**Category:** Real Technical Problem
**Severity:** Medium
**Why it matters:** Flow-completion-ratio features (used by both DDoS and reconnaissance detectors) depend on seeing response-direction traffic (RST/ACK patterns). Depending on where a real mirror/tap is physically placed, only one direction of a link may be visible — the project's own data-requirements task flagged this as an availability caveat, but no fallback exists if this assumption fails to hold at a real deployment site.
**Evidence/reasoning:** Stated explicitly in the data-requirements task as "an availability caveat, not a design decision" — i.e., acknowledged but never resolved.
**Required fix:** None for MVP (the lab is configured to guarantee bidirectional visibility); state this as an explicit deployment-site prerequisite in documentation, not an assumption the system self-verifies.

---

### Issue 14 — JA3 fingerprinting has known, literature-documented weaknesses beyond just "we lack data"
**Category:** Real Technical Problem
**Severity:** Medium
**Why it matters:** Even with full training data, JA3-style fingerprinting is a widely-documented weak signal — many unrelated applications share identical fingerprints because they use the same underlying TLS library, and malware authors can trivially mimic a benign fingerprint. The project's encrypted-malware detection theory has a real ceiling that isn't just a data-availability problem.
**Evidence/reasoning:** This limitation was noted once, briefly, in the threat-decomposition task ("a well-documented technique" for evasion) but its severity is understated relative to how central JA3 is to this detector's design.
**Required fix:** None for MVP; if asked, acknowledge this as a known, literature-documented limitation of JA3-based approaches generally, not specific to this implementation.

---

### Issue 15 — Docker internal-network isolation has not been explicitly verified against lateral reachability
**Category:** Real Technical Problem
**Severity:** Medium
**Why it matters:** The "no return path" architectural-compliance test checks that the capture container cannot reach *external* networks. It does not explicitly verify the capture container cannot reach *other same-host containers* (backend, Redis, database) beyond what's architecturally intended — a narrower guarantee than "no return path" implies at face value.
**Evidence/reasoning:** The verification strategy's architectural-compliance test is framed around egress blocking via a network namespace, not lateral same-host container reachability specifically.
**Required fix:** Add an explicit check that the capture container's network policy prevents it from initiating connections to any other Compose service beyond what's architecturally required (none) — a small addition to the existing test, not new scope.

---

### Issue 16 — No privacy/data-retention policy exists for stored network-identity data
**Category:** Production-Only Concern
**Severity:** Low (for the prototype; would be Medium-High at real deployment)
**Why it matters:** The alerts database stores source/destination IPs and evidence indefinitely for the prototype's lifetime. This is a reasonable prototype default, but the project has no stated policy for what would happen with real IP addresses and traffic metadata about real people/systems at actual deployment — a gap a security-focused judging panel (NTRO context) could reasonably probe.
**Evidence/reasoning:** The backend design explicitly defers retention policy design "since no such constraint has been specified for this project" — true for the prototype, but worth having a one-line answer ready.
**Required fix:** None for MVP; have a stated, one-sentence position ready ("retention/redaction policy is a deployment-site configuration decision, not designed here") rather than being caught flat-footed.

---

### Issue 17 — Overall MVP scope remains large for a student team, even after simplification
**Category:** Acceptable Prototype Limitation
**Severity:** High
**Why it matters:** Even after replacing the multi-VM lab with Docker Compose and trimming ML scope, the remaining build is still substantial: six rule detectors, five-to-six tuned-and-calibrated ML classifiers, a custom streaming pipeline with several nontrivial statistical primitives, a six-entity backend, a six-page dashboard, a Dockerized multi-container lab, a full multi-layer test suite, and a quite specific 15-step rehearsed demo. This is a lot of surface area for a student team to actually finish to the standard documented, regardless of how well-scoped each individual piece is.
**Evidence/reasoning:** Cross-referencing the total component count across the architecture, backend, and UI tasks against typical hackathon team size/time constraints.
**Required fix:** None for MVP as a redesign — the classification/prioritization work already done is sound; the honest risk is execution capacity, not design, and should be managed via ruthless internal prioritization if time runs short (the capability-classification task already provides the ordering for what to cut first).

---

### Issue 18 — DGA traffic-generation script is still unbuilt this late in the project
**Category:** Real Technical Problem
**Severity:** Medium-High
**Why it matters:** The DGA detector's actual demonstrability depends on a script that turns DGArchive domain strings into real queried DNS traffic — named as a task repeatedly across many design documents but never concretely specified or built as of the most recent audit. This is a genuine open implementation risk, not merely a documentation gap.
**Evidence/reasoning:** Flagged unresolved in both the first and second final audits (B2/D1).
**Required fix:** Build this script before attempting to demo the DGA detector live; the demo's own fallback plan (replay-only) should be assumed the default, not a contingency, until this is actually done.

---

### Issue 19 — Live JA3-trigger for the encrypted-malware demo is fragile
**Category:** Acceptable Prototype Limitation
**Severity:** Medium
**Why it matters:** Reproducing a specific pre-registered JA3 hash on demand depends on the exact TLS client library/version used to generate the demo's TLS session. A minor library or configuration difference could silently produce a different fingerprint than the one on the blocklist, causing the rule not to fire — a live failure with no obvious cause to a presenter mid-demo.
**Evidence/reasoning:** JA3 is computed from specific handshake parameters (cipher list, extensions, ordering) that are sensitive to client implementation details.
**Required fix:** Verify and pin the exact client tool/library/version used to generate this demo's TLS session well before the event, and confirm its JA3 hash matches the blocklist entry in rehearsal, not for the first time live.

---

### Issue 20 — Benign traffic used for false-positive testing is thin relative to real enterprise diversity
**Category:** Real Technical Problem
**Severity:** Medium-High
**Why it matters:** The false-positive test suite validates against iperf3/Ostinato/TRex-generated traffic plus a handful of named benign-pattern scenarios (NTP, CDN subdomains, SPF/DKIM, authorized scans). Real enterprise networks have far more application and protocol diversity than this. A low measured FPR against this thin baseline does not strongly predict a low FPR in a real, messier network.
**Evidence/reasoning:** The lab-architecture and rule-baseline tasks both flag this limitation directly ("lacks the application-layer diversity of real enterprise traffic") but the FPR numbers reported later never carry this caveat forward explicitly.
**Required fix:** None for MVP; carry the caveat explicitly into any reported FPR figure — "measured against the lab's benign traffic profile," not an unqualified number.

## 10 Questions a Technically Strong SIH Judge Is Most Likely to Ask

1. "Your false-positive rate is 10%, but what does that mean in absolute alerts per day on a real network with millions of benign flows?"
2. "You trained and tested only on traffic from tools you built the detector to catch — how do you know this generalizes to a real attacker who isn't using hping3 or your sandboxed C2 emulator?"
3. "Your encrypted-malware detection is a blocklist match on a fingerprint you already knew — how would this catch malware using a JA3 you haven't seen before?"
4. "What happens to your DGA and DNS-tunnelling detectors if the network uses DNS-over-HTTPS instead of plaintext DNS?"
5. "Is your throughput number something you actually measured, or a target you haven't benchmarked yet?"
6. "Your C2 detector needs hours of observation to fire — how is that 'near-real-time,' and how would a real SOC use an alert that shows up after the attack window it detected?"
7. "How do you know your passive capture setup genuinely has no way to send anything back onto the monitored network, beyond just not assigning it an IP address?"
8. "Your severity score has fixed weights per threat type — how did you decide DDoS is worse than reconnaissance, and is that number based on any data?"
9. "If this were deployed on a real network, what happens to the IP addresses and traffic metadata you're storing — is there a retention or privacy policy?"
10. "You have seven threat categories but only six with actual ML models — why should this count as an AI-based detection system for the one that doesn't?"
